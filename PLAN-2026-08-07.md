## Task 2 — iOS audio (bug, highest priority)

Diagnosis from code (lib/audio.ts, lib/mp4Recorder.ts, useMediaRecorder.ts):
- The known WebKit failure — *any* mic audio routed through WebAudio comes out
  as pure silence while every API reports success — was fixed **only in the
  MediaRecorder fallback** (raw track on WebKit, commit d7a0b52).
- The **primary WebCodecs path still taps the mic through a WebAudio
  gain/limiter/AudioWorklet graph on every platform** (`createBoostedMicPcm`).
  If WebKit's silence bug applies at the `MediaStreamAudioSourceNode` (it
  does — that's the documented root cause, not the destination node), the tap
  delivers all-zero PCM blocks: `audioFrames > 0`, no error, `audioDropped`
  stays false → clip ships with a silent-but-present AAC track. Exactly the
  reported symptom, with no warning.
- Also: the user's iOS test predates today's deploy — the live site was the
  July 31 build with NONE of the audio fixes. Today's deploy may already fix
  their device via the fallback path. The WebCodecs hole above is still real
  wherever iOS supports AudioEncoder.

Fix (lib/mp4Recorder.ts + lib/audio.ts):
1. Track a running `audioPeak` (max |sample|) inside the onPcm callback —
   trivial cost (48 × 1024 samples/s).
2. On `webAudioTrackIsUnreliable()` platforms only: after the mic tap starts,
   preflight ~400 ms (the 3-2-1 countdown already covers this latency). If PCM
   is exactly all-zero → close the tap, return null → recording falls through
   to MediaRecorder, which on WebKit uses the RAW mic track (proven audible).
   A real mic never delivers exact zeros (noise floor); the WebKit bug does.
3. At stop, `audioDropped` additionally trips when `audioPeak === 0` — on all
   platforms, so a silent-track clip always warns.
4. Test (Playwright, Chromium): record with an audio track derived from a
   silent WebAudio destination (nothing connected) → expect the "no sound"
   warning; record with the normal fake-mic tone → expect no warning.

Honest limit: cannot be verified on real iOS from this machine — Vali must
test on the iPhone. The design guarantees: worst case on WebKit is the
pre-existing MediaRecorder+raw-mic path, which is the one that works.

## Task 4 — Liveliness T2: mouth + blink imitation on the PFP

T1 (whole-head squash/stretch) shipped; Vali wants actual mouth/eye motion.
Design (per the original T2 sketch in memory, scoped to stay 2D-canvas):

- **Anchors**: per-mask eye-L/eye-R/mouth points, normalised to the mask
  image. Sources, in order:
  1. Auto: run FaceLandmarker in IMAGE mode on the PFP art during mask prep
     (model already shipped). Accept only confident detections.
  2. Manual: three draggable pins in the existing mask editor.
  3. None → T2 off for that mask, T1 keeps running. **A mask without anchors
     can never be warped — preserves the "cannot mangle a PFP" guarantee.**
  Persist anchors in the existing IndexedDB mask record next to `placement`.
- **Mouth (jawOpen)**: 3-slice band warp in the existing 2D draw — art above
  the mouth line unchanged; a thin band at the mouth stretches vertically with
  jawOpen; the chin slice below translates down. Classic 2D jaw-drop puppet,
  just extra drawImage calls, no WebGL.
- **Blink**: per-eye eyelid occluder — an ellipse filled with colour sampled
  just above each eye anchor, scaled in with the blink signal. Reads as a
  blink at PFP scale without knowing anything about the art style.
- Both scale with the existing `mask.liveliness` slider; 0 stays exact
  identity. New per-mask toggle "Expressions" (default on when anchors exist).
- Tests: anchors→warp geometry unit-ish tests; identity at liveliness=0;
  editor pin drag persists; no warp without anchors.

## Task 5 — SMB/MonkeDAO birthday game ("5")

Context: SMB Gen2 minted Aug 2021 → 5th birthday now. Follow the Banana Rain
pattern exactly (lib/bananaRain.ts): zero-dep canvas layer drawn into the
compositing canvas (so it's in the recording for free), over camera, under
avatar; gated to the same MonkeDAO/SMB collections; toggle chip next to
Banana Rain in the filter UI.

Game: **Blow Out The Candles**
- A birthday cake rises from the bottom edge: five small candles + one big
  numeral-5 candle, flames flicker procedurally.
- The wearer's real mouth drives it: a sustained `jawOpen` burst (the same
  blendshape signal T1 already consumes — no new detection cost) = a "blow";
  a directional puff extinguishes the nearest lit flame (smoke wisp particle).
- All six out → confetti burst + brief "HAPPY 5TH" ribbon, then candles
  relight after ~4 s so the loop is replayable on camera (TikTok loopability).
- Everything procedural (gradients/paths, like the bananas) — no image assets.
- State machine in `lib/birthdayCake.ts` (pure, testable: tick(dt, jawOpen)),
  drawing separated so tests can drive logic without a canvas.
- Tests: blow sequence extinguishes candles in order; relight cycle; disabled
  → zero draw impact; gating (only SMB/MonkeDAO collections see the chip).

## Task 6 — On-device nano bg-removal (discovery + prototype)

Constraint recap: chroma-key (lib/removeBackground.ts) needs flat-ish
backdrops; Sensei art defeats it. An 11 MB MediaPipe payload was just
deliberately cut — bundle size is a first-class constraint.

Options surveyed:
- **MediaPipe ImageSegmenter** — ALREADY a dependency (@mediapipe/tasks-vision
  ships it; wasm already loads for FaceLandmarker). Models: DeepLabV3 (~2.7 MB)
  or selfie-class models. Trained on photos of people; unknown but plausible
  behaviour on illustrated humanoids. **Zero new runtime → try first.**
- **U²-Netp** (~4.7 MB, salient-object) via onnxruntime-web: best
  quality-per-MB for arbitrary art, but adds the ORT wasm runtime (~5 MB+) —
  only worth it if MediaPipe fails the evaluation.
- RMBG-1.4 / ISNet / BiRefNet: 40 MB+ or non-commercial licences → rejected.

Plan: prototype an **"AI cutout" button in the mask-prep editor only** (lazy
fetch on click; nothing added to the record path or initial load) using
MediaPipe ImageSegmenter + DeepLabV3. Evaluate on real Sensei tokens (plus one
SMB + one Claynosaurz as controls) — measure foreground coverage/mask quality
with the existing cutout-measuring approach from the drive-app skill. Ship the
button only if results are usable; either way write findings + recommendation
(including the u2netp/ORT path with its size cost) into REPORT section below.
The generated matte lands in the same brush-editable mask flow (user can fix
edges — consistent with the user-assisted pivot).
